# Role B 작업 설명: 무엇을 만들었고, 왜 만들었을까?

## 1. 이 프로젝트가 풀려는 문제

창고 직원이 출발점 **S**에서 시작해 필요한 물건 위치들을 방문하고, 마지막에 컨베이어 **C**로 이동한다고 생각해 보자.

```text
출발점 S → 필요한 물건들을 수집 → 컨베이어 C
```

물건을 어떤 순서로 방문하느냐에 따라 걷는 거리가 달라진다. 이 프로젝트는 여러 경로 탐색 알고리즘을 비교해서 다음 질문에 답하려고 한다.

> **작업의 특징에 따라 어떤 알고리즘을 선택하면, 제한된 계산 시간 안에 더 짧은 경로를 얻을 수 있을까?**

여기서 물건의 개수 `n`은 물건의 총 수량이 아니라 **방문해야 하는 서로 다른 위치의 수**다. 같은 위치에서 물건을 여러 개 집더라도 그 위치는 한 번만 방문하면 된다.

Role A가 경로를 계산할 수 있는 알고리즘과 창고 모델을 만들었다면, **Role B는 여러 작업 상황을 만들어 그 알고리즘들을 공정하게 비교하고 결과를 해석하는 역할**이다.

## 2. 이번에 한 일을 한눈에 보기

```text
가상의 작업 만들기
    ↓
작업의 특징 계산하기
    ↓
같은 작업에서 여러 알고리즘 실행하기
    ↓
거리·계산 시간·실패 여부 기록하기
    ↓
개발용 데이터로 알고리즘 선택 규칙 만들기
    ↓
처음 보는 평가용 데이터로 규칙 확인하기
    ↓
결과표와 그래프 만들기
```

이 순서를 실행할 수 있도록 코드를 추가했고, 실제로 합성 작업 **4,050개**를 만들어 실험했다. 합성 작업이란 실제 창고에서 수집한 주문이 아니라, 정해진 규칙으로 컴퓨터가 만든 가상의 주문이다.

## 3. 어떤 작업 상황을 만들었을까?

창고의 구조와 컨베이어 위치는 고정하고, 물건 위치와 출발점을 바꿨다. 그래야 창고 자체가 바뀐 영향과 주문이 달라진 영향을 한꺼번에 섞지 않고 작업 조건을 비교하기 쉽다.

| 바꾼 조건 | 이번 실험의 설정 | 이유 |
|---|---|---|
| 필요한 위치 수 | 3, 5, 7, 8, 10, 12, 15, 20, 50개 | 작은 작업과 큰 작업에서 알고리즘의 속도와 경로 품질이 달라지는지 확인한다. |
| 물건 배치 | 군집형, Random-Stow-like, 방향형 | 가까이 모인 경우와 넓게 퍼진 경우 등에서 차이가 있는지 확인한다. |
| 출발점 | 앞쪽, 중앙, 가장자리의 세 위치 | 같은 물건을 집어도 출발 위치에 따라 경로가 달라질 수 있다. |
| 컨베이어와의 관계 | 물건 집합을 좌우로 반사한 원거리·근거리 쌍 | 비슷한 물건 간 구조를 가진 작업에서 위치 차이를 살펴본다. |

- **군집형**은 인접한 세 통로 안에서 물건 위치를 뽑는다.
- **Random-Stow-like**는 창고 전체의 선반 위치에서 뽑는다. 실제 기업의 재고 배치 방식을 재현한 것은 아니다.
- **방향형**은 창고 뒤쪽 영역에서 뽑는다.
- **원거리·근거리 쌍**은 물건 위치들을 좌우로 뒤집어 만든다. 이때 출발점과 물건 사이 거리도 변하므로, 결과 차이를 컨베이어 거리의 영향 하나로 단정할 수 없다.

총 작업 수는 다음처럼 계산한다.

```text
9개 위치 수 × (3개 기본 배치 + 원거리·근거리 2개) × 3개 출발점 × 30개 seed
= 4,050개 작업
```

`seed`는 난수 생성의 출발값이다. 같은 설정과 seed를 사용하면 같은 작업을 다시 만들 수 있다. 실험을 다른 사람이 확인하거나 나중에 다시 실행하기 위해 기록한다.

## 4. 작업의 특징은 왜 계산했을까?

알고리즘을 선택하려면 각 작업이 어떤 상황인지 숫자나 이름으로 표현해야 한다. 그래서 각 작업에서 아래 다섯 가지를 기록했다.

| 특징 | 쉬운 뜻 | 알아보려는 것 |
|---|---|---|
| `n` | 방문할 서로 다른 위치 수 | 작업이 커질 때 정확한 계산이 얼마나 오래 걸리는가? |
| `dispersion` | 물건 위치들이 서로 얼마나 떨어져 있는지의 평균 | 넓게 퍼진 작업에서 경로 개선이 더 유용한가? |
| `start_mean` | 출발점에서 각 물건까지 거리의 평균 | 출발 위치가 경로 선택에 영향을 주는가? |
| `conveyor_mean` | 각 물건에서 컨베이어까지 거리의 평균 | 물건과 도착점의 관계가 경로 선택에 영향을 주는가? |
| `pattern` | 작업을 만들 때 지정한 배치 종류 | 평균 거리만으로 표현하기 어려운 배치 차이가 있는가? |

거리는 선반을 가로지르는 직선거리가 아니라 **직원이 실제 통로를 따라 이동하는 최단 거리**다. 예를 들어 선반 반대편이 직선으로는 가까워 보여도, 통로 입구까지 돌아가야 한다면 그만큼 더 멀게 계산한다.

`pattern`은 생성기가 붙인 이름이다. 실제 주문의 좌표를 보고 패턴을 자동으로 알아내는 기능은 아직 없다.

## 5. 어떤 알고리즘을 비교했을까?

| 방법 | 간단한 설명 | 역할 |
|---|---|---|
| Given Order | 입력된 순서대로 물건을 방문한다. | 단순한 비교 기준이다. 실제 직원의 이동 성능을 측정한 값은 아니다. |
| NN | 현재 위치에서 가장 가까운 다음 물건을 반복해서 선택한다. | 빠른 기본 방법이다. |
| Exhaustive Search | 가능한 방문 순서를 전부 확인한다. | 완료되면 최적 경로를 알 수 있지만, 위치가 많아지면 계산량이 급격히 늘어난다. |
| DP | 이미 계산한 부분 결과를 활용해 최적 경로를 찾는다. | 완료되면 최적 경로를 보장하지만, 작업이 커질수록 시간과 메모리가 많이 든다. |
| CA-plus / CA-minus | 다음 물건까지의 거리와 물건에서 컨베이어까지의 거리를 함께 고려한다. | 컨베이어 방향을 고려하는 방식이 도움이 되는지 실험한다. 두 방법은 컨베이어 거리의 반영 방향이 다르다. |
| NN 또는 CA + 2-opt | 먼저 만든 방문 순서의 일부를 바꿔 보면서 더 짧은 경로를 찾는다. | 경로를 추가로 개선할 때 얻는 이득과 계산 비용을 비교한다. |

합쳐서 실행 후보는 **9개**다. 후보마다 같은 작업을 주고, 가능한 범위에서 동일한 거리 정보를 사용해 비교한다.

CA 방법의 계수는 컨베이어까지의 거리를 어느 정도 반영할지 정하는 숫자다. 본실험에는 작은 개발용 예비 실험에서 살펴본 값 중 **0.5**를 공통으로 사용했다. 이 값이 모든 작업에서 최선이라는 뜻은 아니다.

## 6. 개발용과 평가용 데이터를 왜 나눴을까?

문제를 풀 때 정답을 먼저 보고 규칙을 만들면, 새로운 문제에서도 그 규칙이 잘 작동하는지 알기 어렵다. 그래서 전체 작업을 두 부분으로 나눴다.

- **개발용 2,025개:** 알고리즘 선택 규칙을 만들고 조정하는 데 사용한다.
- **평가용 2,025개:** 개발이 끝난 규칙을 바꾸지 않고 적용해 성능을 확인한다.

관련된 작업이 양쪽에 흩어지지 않도록 **seed 단위로 묶어서 분할**했다. 예를 들어 같은 물건 위치에서 출발점만 바꾼 작업들은 같은 쪽에 둔다. 각 seed에서 만든 다른 위치 수·배치·반사 작업도 같은 그룹으로 취급한다.

평가용 작업은 2,025개이지만, 서로 관련된 작업들을 묶으면 **15개 seed 그룹**이다. 따라서 불확실성을 계산할 때 2,025개가 모두 서로 독립적인 주문이라고 가정하지 않았다.

## 7. 왜 두 가지 방식으로 시간을 쟀을까?

### 알고리즘 자체 비교

먼저 작업에 필요한 위치 사이의 거리를 한 번 계산한다. 그다음 여러 알고리즘이 같은 거리 정보를 받아 방문 순서를 정하도록 한다.

이렇게 하면 공통 준비 작업의 영향을 따로 두고 **방문 순서를 정하는 알고리즘 자체의 거리와 계산 시간**을 비교할 수 있다.

### 실제 요청에 가까운 비교

실제 요청에서는 알고리즘 실행 외에도 입력 확인, 거리 계산, 경로 복원 등의 시간이 필요하다. 그래서 이 시간도 포함한 요청 전체 시간을 별도로 측정했다.

기존 요청 처리기는 요청한 방법이 오래 걸리거나 제한에 걸릴 가능성에 대비해 **NN 경로를 먼저 확보**한다. 예를 들어 DP가 시간 초과되면 NN 경로를 대신 돌려줄 수 있다. 이것을 *fallback*이라고 한다.

이때 기록을 구분하는 이유는 다음과 같다.

```text
요청한 방법: DP
DP 실행 결과: 시간 초과
실제 반환된 경로: NN
```

NN 경로가 반환됐다고 해서 DP가 성공한 것은 아니다. 그래서 **요청한 방법의 상태**, **실제로 반환한 방법**, **대체 경로 사용 여부**를 따로 저장했다.

## 8. 계산 시간 제한은 왜 넣었을까?

경로가 아주 짧더라도 직원이 경로 계산을 지나치게 오래 기다려야 한다면 실용적이지 않을 수 있다. 그래서 이번 실험에서는 탐색적인 기준으로 **요청당 0.2초**를 사용했다.

이 수치는 실제 창고의 서비스 기준을 조사해 확정한 값이 아니다. 컴퓨터 성능, 실행 중인 다른 작업, 시간 제한 등에 따라 결과는 달라질 수 있다. 알고리즘 자체 비교에서는 공통 거리 준비가 끝난 뒤 탐색에 0.2초를 주고, 요청 전체 비교에서는 요청 처리 전체에 0.2초를 적용했다.

시간 초과나 크기 제한에 걸린 결과도 삭제하지 않고 남겼다. 실패한 작업을 빼고 성공한 거리만 평균 내면, 자주 실패하는 알고리즘이 실제보다 좋아 보일 수 있기 때문이다.

## 9. 어떤 선택 규칙을 만들었을까?

개발용 데이터에서 네 가지 정책을 비교했다.

1. **고정 정책:** 모든 작업에 같은 알고리즘을 사용한다.
2. **개수 정책:** 필요한 위치 수 `n`을 보고 고른다.
3. **숫자 특징 정책:** `n`, 분산도, 출발점 거리, 컨베이어 거리를 보고 고른다.
4. **숫자 특징 + 패턴 정책:** 위 숫자 특징과 생성 시 붙인 패턴을 함께 보고 고른다.

개발 결과, 고정 정책은 **NN+2-opt**를 골랐다. 나머지 세 정책은 우연히 모두 같은 규칙을 골랐다.

```text
필요한 위치가 13개 이하 → DP
필요한 위치가 14개 이상 → NN+2-opt
```

코드에 저장된 기준은 `n <= 13.5`다. `n`은 정수이므로 위와 같은 뜻이다. 이 경계는 **이번 개발 데이터와 0.2초 설정에서 얻은 실험 규칙**이며, 모든 컴퓨터나 모든 창고에 적용되는 기준은 아니다.

개발 데이터 안에서도 관련 작업이 섞이지 않도록 seed 그룹을 나눠 교차 검증했다. 그리고 개발이 끝난 규칙을 저장한 뒤 평가 데이터에 적용했다.

## 10. 평가 결과는 어떻게 읽어야 할까?

평가용 2,025개 작업에서 네 정책은 모두 제한 시간 안에 경로를 반환했다.

| 정책 | 경로 거리의 중앙값 | 요청 전체 시간의 중앙값 |
|---|---:|---:|
| 항상 NN+2-opt | 156m | 약 2.41ms |
| 위치 수로 선택 | 152m | 약 3.47ms |
| 숫자 특징으로 선택 | 152m | 약 3.47ms |
| 숫자 특징과 패턴으로 선택 | 152m | 약 3.48ms |

`ms`는 밀리초이고, 1,000ms가 1초다. 중앙값은 결과를 크기순으로 놓았을 때 가운데 값이다.

같은 작업끼리 짝지어 비교했을 때, 위치 수로 선택한 규칙은 고정 NN+2-opt보다 **평균 1.43m 짧았다**. 15개 seed 그룹을 기준으로 계산한 95% 부트스트랩 구간은 **1.23~1.63m**였다. 이는 그룹을 여러 번 다시 뽑아 평균 차이가 얼마나 흔들리는지 살펴본 범위다. 평가 그룹 수가 적고 작업도 합성이므로 결과를 실제 창고 전체에 그대로 일반화할 수는 없다.

중앙값의 차이 `156 - 152 = 4m`와 평균 절감 `1.43m`는 서로 다른 계산이다. 전자는 두 정책의 중앙값을 각각 구해 비교한 것이고, 후자는 **작업마다 거리 차이를 구한 뒤 평균**을 낸 것이다.

이번에는 숫자 특징과 패턴을 추가한 정책도 위치 수만 쓰는 정책과 같은 규칙을 골랐다. 따라서 **추가 특징이 성능을 높였다는 근거는 아직 없다.**

알고리즘 자체 비교에서는 Exhaustive Search와 DP가 모두 끝난 평가 작업 675개에서 두 방법의 거리가 일치했다. DP는 0.2초 탐색 제한에서 n=15인 평가 작업 225개가 시간 초과됐고, n=20과 50은 현재 설정된 크기 제한에 걸렸다. 별도의 2초 메모리 표본에서는 n=15가 완료됐다. 시간 제한과 프로그램에 설정된 크기 제한을 구분해서 해석해야 한다.

전체 실행 방법은 [Role B 실험 방법](08-role-b-experiments.md), 수치와 해석은 [Role B 평가 결과](09-role-b-results.md)에 정리했다. 결과 파일은 덮어쓰지 않도록 만들어져 있으므로 재실행할 때는 새로운 출력 폴더를 사용한다.

기존 기능과 새 실험 코드의 테스트는 프로젝트 최상위 폴더에서 다음 명령으로 실행한다.

```bash
python3 -m unittest discover -s tests -v
```

이번 작업 후에는 **33개 테스트가 통과**했다. 원시 결과를 포함한 `results/` 폴더는 약 190MB이므로, 저장소에 올리기 전에 팀과 파일 관리 방식을 정하는 것이 좋다.

## 12. 지금 완료된 것과 남은 것

완료된 것은 가상 작업 생성부터 특징 계산, 알고리즘 비교, 규칙 학습, 평가 데이터 검증, 결과표와 그래프 생성까지의 **오프라인 실험 흐름**이다.

현재 선택 규칙은 기존 요청 처리기에 자동 연결되지 않았다. 평가 코드에서는 특징 계산을 위해 거리를 한 번 준비한 뒤 요청 처리기에서 다시 준비하므로, 실제 서비스에 통합할 때는 이 중복을 줄이고 전체 시간을 다시 측정해야 한다. Streamlit UI도 별도 작업으로 남아 있다.

실제 창고 데이터, 다른 창고 구조, 다른 시간 예산과 더 많은 독립 seed 그룹에서 같은 경향이 나타나는지는 아직 확인하지 않았다.
